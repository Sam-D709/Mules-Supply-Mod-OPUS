# M4 简要日志与 Debug

适用于本地测试版 **0.1.0-beta.7 / 内部669**。本次行为与阈值见[beta.7说明](releases/v0.1.0-beta.7.md)，历史反馈见[分析报告](BETA6_FIXES.zh-CN.md)。

## 默认船只日志

在对应船的 **信息 → 日志** 查看以`M4 · 船号`开头的记录，无需启动参数。标题直接说明派单成功、装载不足、无可用方案、搜索未完成或提交失败。

正文先显示最终结果，再显示组合体积、装载率和真实副单尝试，最后列出商品、数量、供应站与收货站。不再重复整页设置、布尔开关或与最终失败无关的候选统计。

例如提交时被其他交易抢走余量：

```text
M4 · SWQ-407 · 提交失败
提交失败：某供应站的某商品余量不足，计划62件，现可用24件。
组合：1笔，12400 / 12400 m³，装载100%；要求75%。
副单未扩展：当前草案已满仓。
第1笔：某商品 × 62，某供应站 → 某收货站。
```

这是格式示例，数字来自旧存档中的失败情形；不是beta.5原生运行记录。提交失败下的组合和商品列表是未成功派出的草案。“已满仓”指规划当时的草案，不代表提交时仍有足够货物。beta.5刷新净货量以减少此类草案，但最终复核仍可能遇到报价变化。

副单摘要会区分：

| 显示 | 含义 |
|---|---|
| 尝试N次扩展，M次可加入候选方案 | 实际执行了主单之后的组合扩展；含不同主单/组合的尝试，M不是已执行的副单数量 |
| 每趟上限设为1笔 | 玩家限制了副单 |
| 当前草案已满仓 | 此草案无需继续加货；若随后提交失败，仍属于提交失败 |
| 未找到可用主单 | 尚未进入有主单的组合阶段 |
| 搜索额度耗尽 | 本轮未完整搜索，不计作一次完整装载不足 |
| 没有同收货对象、同仓型且仍有余量的其他候选 | 已找到主单，但当前候选无法进入副单扩展 |

搜索失败时只补充相关的价差、走廊或路径汇总。它们是**检查次数**，不是去重后的工厂数，也不是全部失败原因的穷举；只检查到第一个失败条件。旧版“价格失败中的副单搜索次数”已经删除，它没有正确统计新版搜索过程。

连续三次完整搜索只有装载不足，下一轮临时放宽装载率。另外等待满2/5/10游戏分钟时，本轮门槛上限为50%/25%/0%；分级等待满90游戏秒或三轮未获任务即允许跨档主单。其他限制不变，搜索不完整不增加计数。成功始终记录；失败对同一配置、基点和失败类别冷却10游戏分钟，失败类别改变立即记录。同次提交失败不再额外生成一份相同待命简报。行为页仍更新当前失败。

## 开启本次测试的 Debug

1. 在 Steam → X4属性 → 启动选项末尾加入 **`-scriptlogfiles`**。
2. **完整退出并重新启动X4**，加载测试存档副本。只回主菜单不足以保证重新载入更新的脚本。
3. 打开 **扩展选项 / Extension Options → Mules-Supply-Mod-OPUS → Debug：详细磁盘日志**。
4. 等待新一轮搜索后复现，记录开始和结束存档。已有排队订单无法追补历史搜索。
5. 本机日志位置：

```text
C:\Users\SCP343\Documents\Egosoft\X4\1112832858\logs\MulesExtended\debug.txt
```

其他电脑在实际X4用户目录的`logs\MulesExtended\debug.txt`。检查文件修改时间和新增内容，避免把旧日志当成本轮结果。文件继续追加；如需独立文件，可在游戏退出时先将旧文件改名保存。测试结束后关闭Debug。

菜单需要可选的 **SirNukes Mod Support APIs**，核心采购及普通船只日志无需该依赖。缺少`-scriptlogfiles`时，仅打开菜单开关不会创建磁盘日志。Debug开关跟随存档保存，默认关闭；不必开启全游戏调试输出。

## 如何读 Debug

每轮船只搜索的共同前缀：

```text
M4 t=386800 ship=SWQ-407 attempt=42 relaxed=0 EVENT ...
```

`t`为`player.age`游戏时间秒数，所有这些搜索事件均带此时间戳。可与存档头的游戏时间对齐；开启Debug前的过程无法追补，不必与存档操作同时完成。`t`不是电脑现实时间，SETA会加速其增长。`ship`为船号，`attempt`为该驾驶员的搜索序号，`relaxed`表示本轮是否临时豁免装载率。多船记录会交错，按 **船号 + attempt** 合看同一轮；序号不是跨驾驶员/跨存档的全局ID。

| 事件 | 用途 |
|---|---|
| BEGIN | `build=beta.7`、本轮基点、最低装载率、笔数上限、范围、玩家优先及候选轮换位置 |
| CANDIDATE | 需求/货源标识及站名、商品、可运量、净需求/供货、实际价格与接受/拒绝原因 |
| EXTEND | `depth=1`尝试主单，`depth>1`真实尝试副单；`result`说明成功、货量/预算、报价失效、走廊或路径失败 |
| RETURN_POLL / RETURN_SEARCH | 返航轮询与实际启动搜索的游戏时间；前者的lastSearchAgo可定位长时间未搜单；不属于attempt |
| LIMITS | 等待秒数、有效门槛、跨档候选及候选供需上界，同收货对象/走廊/笔数/预算限制 |
| REPAIR | 修复是否达标、修复体积、有效门槛、额外检查数和补入笔数 |
| END | 规划结束状态、耗时、检查/扩展计数、两种额度是否耗尽、体积及效率；**不表示实际派单成功** |
| DRAFT_LEG | 最佳草案每笔商品、货源、需求、数量和规划价格 |
| COMMIT_CHECK | 提交复核的具体失败，含变化后的数量、资金、仓容、规则或价格信息 |
| COMMIT | 创建订单阶段的最终状态和订单数；复核提前失败时可能没有此事件 |
| COMMIT_LEG | 创建阶段每笔商品、提交价格及买卖订单标识；失败时需结合总状态，不能当作成功运输 |
| QUEUE | 提交后的实际订单队列，便于检查采购在前、交付在后 |
| RESULT | 本轮实际结果；成功收尾在commit返回前完成，不再依赖父脚本恢复；即使普通日志处于冷却，也保留记录 |

正常顺序为`BEGIN → CANDIDATE → EXTEND → END → DRAFT_LEG → COMMIT/COMMIT_LEG → RESULT`。复核失败可在`COMMIT_CHECK → RESULT`结束；无方案则`END → RESULT`。中途船只配置变化也会终止。需求预过滤还有带同一前缀的说明行。

数量以件计，`volume`为m³，价格为Cr；`eta`只是按跳数和装卸权重估算的相对秒数，`score`为体积除以该权重时间，不是游戏原生ETA。`secondaryTried/secondaryAdded`包含不同替代方案，实际派单笔数应看最终成功记录和订单。

`NET`行的船号属于占额所属船，不一定是当前搜索船；用于检查模组占额何时由原生预订接管。`DISCOVER/ROSTER`是共享索引/成员事件，带时间和基点，不属于某个驾驶员的attempt。

删除旧启动参数长清单和重复REJECT行，拒绝原因合并到CANDIDATE/COMMIT_CHECK。异常终止可出现`RESULT status=aborted success=false reason=script_interrupted`；它表示尝试被中断，不代表已创建订单必定撤销。行为失败提示只显示船号和具体原因。

Debug沿用原计算结果，不追加候选、价格或路径查询，不改变择单规则。关闭时跳过详细文字生成。开启仍会增加磁盘写入，建议只在复现窗口启用。

## 验收

- 同次提交失败在普通日志只保留一份摘要，首行直接给出失败与具体数值。
- 比较“有副单扩展但被拒”和“主单满仓/笔数上限导致没有扩展”；不得再出现旧的错误0计数。
- 对同一船号和attempt，核对草案、提交及RESULT；界面冷却不应导致磁盘缺失最终结果。
- 连续装载不足的第四轮可解限；搜索额度耗尽不能计入三次失败，但不重置等待时间。
- 核对RETURN_POLL、RETURN_SEARCH和BEGIN的时间，遇袭时可推迟，空闲正常移动不应再出现约11分钟才重搜。
- 确认分级后仍有副单扩展；修复成功时RESULT体积和COMMIT_LEG一致。
- 分别完成SETA开启30现实分钟和关闭1现实小时的起止存档窗口；压力测试后再分析动态测试环境。
- 关闭Debug后新详细行停止；英文界面无缺失文本。

本地XML适配器不能验证原生磁盘刷新、界面渲染或SETA性能。beta.7仍需上述游戏内复测。
