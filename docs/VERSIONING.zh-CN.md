# 版本命名与发布指南

本项目从 **`v0.1.0-beta.1`** 开始使用独立版本号。原模组的6.60以及本项目早期沿用的6.62是来源和开发记录，不再作为新安装包的公开版本。

## 两套编号分别维护

| 位置 | 首次公开发布值 | 用途 |
|---|---|---|
| 根目录 `VERSION` | `0.1.0-beta.1` | 公开版本的唯一来源，不加前缀v；打包工具据此命名 |
| Git标签、Release标题 | `v0.1.0-beta.1` | 定位对应源码提交 |
| 安装包 | `Mules-Supply-Mod-OPUS-v0.1.0-beta.1.zip` | 提供给玩家解压安装 |
| `content.xml` 的 `version` | `663` | X4内部数字版本；沿用已有662继续递增 |
| `content.xml` 的 `date` | `2026-10-23` | 本次发布日期，格式YYYY-MM-DD |

公开版本和X4数字版本不做数值换算。游戏扩展列表可能把内部663显示成6.63，这是内部版本的显示形式；下载版本以VERSION和Release标题为准。不要把内部版本改成1或0.1.0，以免格式不合法或被认为降级。保持原扩展ID `ws_2013772865` 不变。

AI脚本的 `<aiscript version="…">` 又是独立的存档迁移版本：只有相应脚本变更、需要迁移时才调整，不要随公开发布统一改写所有脚本版本。

## 何时使用什么版本

格式为 `主版本.功能版本.修订版本[-测试阶段.轮次]`。本项目使用没有前导零的整数，测试阶段限定为alpha、beta或rc，轮次从1开始。

| 情况 | 示例 |
|---|---|
| 主要功能未完成的早期实验 | `0.1.0-alpha.1` |
| 主要功能可用，公开收集测试反馈 | `0.1.0-beta.1` |
| 同一轮功能修复后继续测试 | `0.1.0-beta.2`、`0.1.0-beta.3` |
| 功能冻结，准备验收 | `0.1.0-rc.1` |
| 这一轮通过验收 | `0.1.0` |
| 验收后仅修复问题 | `0.1.1`，需要测试时先用`0.1.1-beta.1` |
| 增加下一批功能或改变重要行为 | `0.2.0-beta.1` |
| 整体达到认可的稳定和兼容程度 | `1.0.0` |

测试版不一定必须以0开头；这里的0表示项目仍在早期发展。后缀beta表示本次发布是测试版。即使成为0.1.0，它也只代表这一轮功能验收，不承诺未来所有0.x版本接口不变。1.0以后，再按重大不兼容变更升主版本、兼容新功能升功能版本、修复升修订版本。

## 下一次发布怎么做

下面以 **`v0.1.0-beta.4` / 内部666** 为例。如果666已经发布过，应继续用更大的内部版本。只在模组源码仓库执行这些操作，不要对整个X4游戏目录提交。

1. 同步远端并确认分支，保留他人README等修改；先完成代码和游戏验证。
2. 将VERSION改为`0.1.0-beta.4`，将content.xml内部版本改为`666`、日期改为当天日期。同步中英文README的下载链接及包名。
3. 新建`docs/releases/v0.1.0-beta.4.md`，写清触发问题、修复后的行为、验证结果、已知限制与安装方法；更新变更记录。
4. 在仓库根目录验证并打包：

   ```powershell
   python tests/checks.py
   python tests/test_package.py
   git diff --check
   python tools/build.py
   ```

   XML变动还应执行`tools/validate.ps1`，传入本机提取的原版模式目录和AI脚本目录。完整命令参数见该脚本；不同电脑的原版提取路径不同。

5. 查看`dist/build.json`：公开版本、内部版本、安装文件夹、包名和校验结果应正确。解压ZIP，确认顶层只有`mules_and_warehouses_extended`，它里面直接有content.xml和ext_01.cat/dat。干净升级时先移走旧模组文件夹；不要同时启用原版和本分支。
6. 检查`git status`和差异，只提交本轮源码、文档和必要测试。**不提交dist、备份、游戏存档、磁盘日志、个人凭据或诊断转储。** 推送当前功能分支并创建或更新PR，确认准备发布的完整提交SHA。
7. 给该提交打不可变标签，推送标签后创建Release。下面命令中的`提交SHA`须替换为真实值，发布说明文件也必须已经存在：

   ```powershell
   git tag -a v0.1.0-beta.4 提交SHA -m "Mules-Supply-Mod-OPUS v0.1.0-beta.4"
   git push origin v0.1.0-beta.4
   gh release create v0.1.0-beta.4 dist/Mules-Supply-Mod-OPUS-v0.1.0-beta.4.zip dist/SHA256SUMS.txt --verify-tag --prerelease --title "v0.1.0-beta.4" --notes-file docs/releases/v0.1.0-beta.4.md
   ```

   在网页发布也可以：选择对应标签，上传两个附件并勾选**Set as a pre-release**。正式版移除测试后缀并取消预发布勾选；不能仅取消勾选却继续使用beta标签。

8. 下载已发布附件，按SHA256SUMS核对。Issues用于收集问题和反馈，在相关Issue中链接新Release、说明修复及剩余验证项；安装包统一放Releases，不放Packages。

已发布的标签、包和版本号不覆盖、不删除重发。有问题发布下一轮beta；即使只更换发布包内容，也应新建版本，让玩家能准确报告所用版本。内部数字版本也随每次新发布递增，包括beta转正式版。

本地构建只生成dist文件，不会自动提交、上传或替换正在使用的游戏模组。
