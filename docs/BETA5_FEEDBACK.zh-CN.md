# beta.4存档3→4反馈与beta.5修正

分析对象为本次更新后的`save_003.xml.gz`和`save_004.xml.gz`：前者为beta.4本轮测试初始状态，后者为结束状态。存档只读，未修改。beta.5尚未在原生X4/SETA重放，以下区分原始证据与本地回归结果。

## 存档和日志显示什么

两存档游戏时间分别为384296.683与386755.261，间隔2458.578秒，约41分钟。两端均有34艘M4；快照中有订单的船从32艘变为14艘。该数字只表示两瞬间的状态，不能计算窗口平均利用率，也不能构成beta.3与beta.4的受控性能比较。

此窗口新增329份M4摘要：

| 类别 | 数量/结果 |
|---|---|
| 成功派单 | 60次：45次一笔、15次两笔 |
| 提交失败 | 118次：74次净数量变化、40次报价不可用、4次价差不满足 |
| 待命摘要 | 151条，其中111条是同次提交结果之后又写的重复待命摘要 |
| 正文长度 | 609～871字符，平均约685字符 |

因此副单并非完全未搜索：除了成功两笔的记录，UIN-813的一份失败日志同时写着“副单超出主路径偏离范围10次”和“副单搜索0次”。后者实际是一个没有正确递增的旧价格细分计数，不能表示新版副单搜索次数。

SWQ-407、DPJ-719、HKB-898等船出现过62件×200m³的满仓草案，提交复核时只剩24件。原规划认为主单已满，所以没有在该状态继续扩展副单；最后失败属于提交余量变化。不能把此类日志解释成“已按最新货量确认装不满却拒绝搜索副单”。

两端均未残留全局锁；存档4仅有1项待接管占额，不支持“大量挂死占额拖住所有船”的解释。活跃基点有34名成员、需求条目21→23；另有两个0成员的旧基点保留大量历史需求，不应将它们当成当前船队实际搜索的全部需求。部分空闲船的保存栈正处于候选收集阶段，不能由某一刻无订单断定没有运行。

本机磁盘`logs/MulesExtended/debug.txt`最后修改于10月23日，不属于本轮beta.4窗口。因此本轮以存档中的日志和脚本状态为证据，没有把旧Debug当作新测试结果。

## 确认并修正的两个规划问题

**候选额度耗尽截断副单。** beta.4用同一`budgetExhausted`同时表示候选筛选额度和路线扩展额度。配对检查到192次后，即使已收集到可拼单候选，也会提前退出后续路线组合。beta.5分离`candidateBudget`与`routeBudget`：候选采集停止后，仍可在128次路线扩展额度内拼单。任何额度耗尽仍标记搜索不完整，不增加连续装载不足次数。

**搜索让出后沿用旧货量。** 多船交错规划时，早先候选中的净量可能已经被其他贸易消耗，导致旧满仓主单继续竞争。beta.5在组合排序前刷新不同需求/货源的净量，每次有限扩展再次读取净需求和供货，结合方案已用数量、资金和仓容重新限制数量。无需增加价格查询，刷新受原搜索上限约束。

安装中的beta.4 CAT/DAT与修改后的beta.5实际XML分别运行这两项回归：beta.4两项失败、beta.5两项通过，均无测试错误。证据在本机`support/seta_save03_analysis/beta4_feedback/before_after.json`。这是可复现的代码问题证据，不是原生引擎修复率测量。

## 日志修改

普通日志以最终失败开头，明确报价失效、计划/现可用量、预算、价差、仓容或订单创建失败；不再附带整段设置和无关候选拒绝。删除同次提交失败后的重复待命摘要。失败按类别、配置和基点冷却10游戏分钟，类别变化立即显示，成功始终记录。

副单改为记录真实扩展次数与可加入方案次数；没有搜索时解释笔数上限、主单满仓、没有主单、没有兼容余量候选或搜索额度耗尽。它们是替代组合检查数，不是实际执行的副单数。

Debug增加游戏时间、船号与尝试编号，串联候选、主/副单扩展、规划终态、草案、提交明细及最终结果。界面冷却不抑制磁盘RESULT，便于下一次按同轮搜索还原失败链。操作与字段见[日志指南](SHIP_LOG.zh-CN.md)。

## 验证和剩余边界

159项本地XML检查通过，含本次10项新增回归；安装包2项检查通过；原版模式验证31个XML、3处补丁选择器。安装清单另保存源码测试哈希与归档逐字节匹配结果。

beta.5不能保证消除所有提交失败：NPC交易、原生预订、动态报价和其他船仍可在规划与提交之间改变可交易量。最终复核保持严格，失败后重新搜索，不把不成立的草案强行下单。路线与候选仍是有限搜索，不保证全局最优。是否提高SETA持续派单率、降低上述118类失败，需要完整重启后从相同存档副本进行新一轮原生复测。
